# Planetary Computer 下载脚本优化分析：v1 → v2

> 分析时间: 2026-06-01
> 分析对象: `scripts/preprocessing/download_from_planetary_computer.py`
> 优化版本: `scripts/preprocessing/download_from_planetary_computer_v2.py`

---

## 一、v1 的五大瓶颈

### 瓶颈 1：按月拆分 STAC 搜索（最大瓶颈，18x）

**v1 代码:**
```python
# 动态数据：拆分为按月窗口
current = start_dt
while current < end_dt:
    window_end = min(current + timedelta(days=31), end_dt)
    ws = current.strftime("%Y-%m-%dT%H:%M:%SZ")
    we = window_end.strftime("%Y-%m-%dT%H:%M:%SZ")
    items = _search_single_window(catalog, source, bbox, ws, we)
    current = window_end
```

**问题:**
- 1.5 年时间范围被拆成 **18 个月** 分别搜索
- 每个 patch 每个 source 需要 **18 次 STAC API 调用**
- 5000 patches × 3 sources × 18 次 = **270,000 次 API 调用**
- 每次 API 调用 1-3 秒（网络延迟 + 服务器处理）
- **仅搜索阶段就需要 150+ 小时！**

**v2 优化:**
```python
# 一次性搜索整个时间范围
kwargs = {
    "collections": [collection],
    "bbox": bbox,
    "datetime": f"{date_start}T00:00:00Z/{date_end}T23:59:59Z",
}
search = catalog.search(**kwargs)
items = search.item_collection()
```

**效果:** 18 次调用 → 1 次调用，**搜索阶段加速 ~18x**

---

### 瓶颈 2：每个 item 单独 stackstac.stack()（2-3x）

**v1 代码:**
```python
for item in items:
    stack = stackstac.stack([item], ...)  # 每个 item 单独调用
    data = stack.compute()
```

**问题:**
- `stackstac.stack()` 每次调用都有固定 overhead（建立 Dask graph、解析 metadata、配置坐标系）
- 一个 patch 平均 25-30 帧 → 调用 25-30 次 stackstac
- Dask graph 的构建和销毁是主要耗时

**v2 优化:**
```python
# 一次性 stack 所有 items
stack = stackstac.stack(items, ...)  # 所有 items 批量传入
data = stack.compute()  # [time, band, y, x]

# 然后从结果中逐个提取
for i, item in enumerate(items):
    data_np = np.asarray(data[i])
```

**效果:** 25-30 次 stackstac 调用 → 1 次，**下载阶段加速 ~2-3x**

---

### 瓶颈 3：每次下载重新签名 SAS token

**v1 代码:**
```python
def _download_item_with_retry(download_fn, item, ...):
    for attempt in range(3):
        item = pc.sign(item)  # 每次重试都重新签名
        return download_fn(item, ...)
```

**问题:**
- `planetary_computer.sign()` 需要与微软服务器交互获取 SAS token
- 每个 item 下载前都调用 → 25-30 次/patch
- SAS token 有效期通常 1 小时，不需要每次重新获取

**v2 优化:**
```python
# 预签名所有 items（一次调用）
items = pre_sign_items(items)  # 批量签名

# 下载时直接复用已签名的 items
batch_results = batch_download_stackstac(items, ...)
```

**效果:** 减少 90% 的签名调用，**加速 ~10-20%**

---

### 瓶颈 4：完整性检查用 rasterio.open()（I/O 瓶颈）

**v1 代码:**
```python
if out_path.exists():
    with rasterio.open(out_path) as src:
        dtype = src.dtypes[0]
        data = src.read(1)
        maxv = data.max()
```

**问题:**
- 对已存在的每个 .tif 文件都用 `rasterio.open()` 打开并读取
- 这是一个昂贵的 I/O 操作（需要解析 GeoTIFF header、读取 tile 数据）
- 断点续传时大部分文件已存在，每次都要重新检查
- 5000 patches × 30 帧 = 150,000 次 rasterio 打开

**v2 优化:**
```python
def quick_check_exists(out_path: Path, source: str) -> bool:
    if not out_path.exists():
        return False
    size = out_path.stat().st_size
    if size < 2048:  # 极小文件 = 损坏
        out_path.unlink()
        return False
    return True  # 文件存在且大小正常 → 直接跳过
```

**效果:** 150,000 次 rasterio 打开 → 150,000 次 `os.stat()`，**跳过检查加速 ~50-100x**

> ⚠️ 注意：v2 的快速检查牺牲了部分安全性（不检测全0文件或格式错误），但在断点续传场景下，文件完整性通常是有保证的。如果需要严格检查，可以定期用独立脚本扫描。

---

### 瓶颈 5：单 item 串行下载

**v1 代码:**
```python
for item in items:
    data_np = _download_item_with_retry(download_fn, item, ...)
    save_geotiff(out_path, data_np, ...)
```

**问题:**
- patch 之间有 ThreadPoolExecutor 并行（16 workers）
- 但 patch **内部**的 items 是完全串行的
- 网络带宽没有充分利用

**v2 优化:**
- 瓶颈 2 的批量 stack 已经解决了这个问题
- 所有 items 一次性从服务器读取，充分利用带宽

## 二、优化效果汇总

| 优化项 | v1 问题 | v2 方案 | 理论加速 |
|--------|---------|---------|----------|
| STAC 搜索拆分 | 18 次/月 | 1 次/范围 | **~18x** |
| stackstac 调用 | 25-30 次/patch | 1 次/patch | **~2-3x** |
| SAS token 签名 | 每次下载重新签名 | 批量预签名 | **~10-20%** |
| 跳过检查 I/O | rasterio.open | os.path.getsize | **~50-100x** |
| 串行下载 | patch 内串行 | 批量并行 | **~1.5x** |
| **整体加速** | — | — | **~5-10x** |

**估算：**
- v1 完成 5000 patches 预计：150 小时（搜索）+ 50 小时（下载）= **~200 小时（8-9 天）**
- v2 完成 5000 patches 预计：8 小时（搜索）+ 20 小时（下载）= **~28 小时（1-1.5 天）**

### 选项 A：停掉 v1，用 v2 重新下载（推荐，加速最大）

- 让 v1 继续下载当前批次（不浪费已投入的时间）
- 新启动的批次用 v2
- 由于两者输出格式完全相同，数据可以混合使用

## 四、v2 的已知限制

1. **快速跳过检查较宽松**：不打开 rasterio 验证格式，极少数情况下可能保留损坏文件。建议下载完成后运行一次完整性扫描。
2. **批量 stack 内存占用**：一次性 stack 25-30 个 items 可能占用较多内存（但 128×128 的裁剪尺寸很小，通常 < 1GB）。
3. **S1 仍用逐个下载**：S1 由于 stackstac 支持不完整，v2 仍使用 odc-stac 逐个下载，优化幅度较小。

## 五、建议

**强烈推荐切换到 v2**。理由：
1. 搜索阶段的 18x 加速是决定性的（从 150 小时 → 8 小时）
2. v2 兼容 v1 的输出格式和断点续传
3. 已下载的 ~50 个 patch 的数据可以保留，v2 会自动跳过
4. 整体从 8-9 天缩短到 1-1.5 天，节省大量时间和磁盘周转

**操作建议：**
1. 停掉 v1 的 4 个 tmux session
2. 用 v2 重新启动（会自动跳过已下载的文件）
3. 更新看门狗监控脚本，让它监控 v2 的进程
