# 2025年数据缺失调查报告

> 调查时间: 2026-05-16
> 调查范围: S2 / S1 / Landsat 在 2025 年的时空覆盖完整性

---

## 一、核心发现摘要

| 数据源 | 缺失月份 | 缺失比例 | 根因 | 是否可补全 |
|--------|---------|---------|------|-----------|
| **S2** | 2025年11-12月 | **424/424 (100%)** | 下载脚本 `DATE_END="2025-10-31"` | ✅ 可补全 |
| **S1** | 2025年7月 | **424/424 (100%)** | 待验证（GEE数据归档延迟或下载异常） | ⚠️ 需先验证 |
| **Landsat** | 2025年3月 | **298/424 (70%)** | Landsat 轨道覆盖特性（正常） | ⚠️ 部分可补 |
| **Landsat** | 2025年7月 | **332/424 (78%)** | Landsat 轨道覆盖特性（正常） | ⚠️ 部分可补 |

**关键结论**: S2 的 11-12 月缺失是**人为的日期限制**，不是数据可用性问题。S1 的 7 月缺失需要验证 GEE/PC 上数据是否存在。

---

## 二、逐项根因分析

### 2.1 S2 — 2025年11-12月完全缺失

**证据:**
- 原始数据 `/workspace/raw/harbin_scenes/s2` 中 `find -name "202511*.tif"` = 0
- 所有 424 个 patch 均无 11-12 月数据
- S2 下载进度文件 `.progress_scenes_s2.json` 最后一个条目: `patch_000423_20251006`

**根因:**
```python
# download_from_planetary_computer.py 第64行
DATE_END = "2025-10-31"

# download_heilongjiang_v11.py 第93行
DATE_END = "2025-10-31"
```

下载脚本统一设置了截止日期为 **2025-10-31**，因此 11-12 月数据根本没有被请求下载。

**不是云筛选导致！** 云筛选脚本 `filter_cloudy_frames.py` 只在已有数据上操作，不会删除月份。

---

### 2.2 S1 — 2025年7月完全缺失

**证据:**
- 原始数据 `/workspace/raw/harbin_scenes/s1` 中 `find -name "202507*.tif"` = 0
- 所有 424 个 patch 均无 2025年7月数据
- 但 2024年7月有 26 个 patch 有数据（证明该区域在7月有S1覆盖）
- S1 有 2025年11-12月数据（证明下载时间范围超过10月）

**根因（两种可能）:**

**可能A: GEE/Planetary Computer 数据归档延迟**
- S1 数据在 GEE 上的发布可能有延迟
- 下载时（约2025年4月）2025年7月的数据尚未归档
- 如果现在（2026年5月）查询，数据可能已可用

**可能B: 下载脚本异常**
- S1 的下载可能在 2025年7月遇到批量错误（网络/GEE服务问题）
- 但 `.errors_scenes_s1.json` 为空，不支持此假设

**验证方法:**
需要先在 GEE 或 Planetary Computer 上手动查询 2025年7月哈尔滨区域的 S1 数据是否存在。

---

### 2.3 Landsat — 2025年3月/7月大面积缺失

**证据:**
- 2025年3月: 仅 126/424 patch 有数据 (30%)
- 2025年7月: 仅 92/424 patch 有数据 (22%)
- patch_000000 的 Landsat 2025年: 1,2,4,5,6,8,9,10,11,12月有数据，**3月和7月缺失**

**根因:**
Landsat 8/9 的重访周期为 **16 天**，且受以下因素影响：
1. **轨道覆盖**: Landsat 轨道不保证每16天覆盖所有地点，某些 patch 在某些月份确实无过境
2. **数据质量过滤**: 下载脚本可能过滤了云覆盖过高的帧
3. **数据可用性**: 某些日期的数据在 GEE/PC 上可能尚未处理完成

**这不是异常！** Landsat 的不均匀覆盖是正常现象。但部分缺失的 patch 可能可以通过扩大搜索窗口或换数据源补全。

## 四、补全计划

### 4.1 优先级矩阵

| 优先级 | 任务 | 预计数据量 | 预计时间 | 难度 |
|--------|------|-----------|---------|------|
| **P0** | S2 2025年11-12月补下载 | ~2,000帧 | 6-8小时 | 低 |

### 4.2 详细步骤

#### 任务1: S2 2025年11-12月补下载

**步骤:**
1. 修改 `download_from_planetary_computer.py` 第64行:
   ```python
   DATE_END = "2025-12-31"
   ```
2. 或使用命令行参数覆盖:
   ```bash
   python scripts/preprocessing/download_from_planetary_computer.py \
       --patches /workspace/raw/harbin_scenes/patches_meta.json \
       --output /workspace/raw/harbin_scenes \
       --sources s2 \
       --date-start 2025-11-01 \
       --date-end 2025-12-31 \
       --workers 4
   ```
3. 云筛选: 运行 `filter_cloudy_frames.py` 处理新下载的 S2 数据

**预计数据量:**
- 424 patch × 2月 × ~2-4帧/月 = ~2,500帧
- 原始大小: ~2.5GB
- 云筛选后: ~850MB

---

#### 任务2: S1 2025年7月验证与补下载

**步骤1 — 验证数据可用性:**

collection = ee.ImageCollection("COPERNICUS/S1_GRD") \

**步骤2 — 若数据存在，补下载:**

**预计数据量:**
- 424 patch × ~2-3帧 = ~1,000帧
- 原始大小: ~500MB

## 五、风险与替代方案

### 5.1 风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|
| GEE/PC 下载配额耗尽 | 中 | 下载中断 | 使用 resume 断点续传 |
| S1 7月数据确实不存在 | 中 | 无法补全 | 提前验证，避免无效工作 |
| 磁盘空间不足 | 低 | 下载失败 | 当前剩余空间 >500GB，充足 |
| 网络不稳定 | 中 | 下载速度慢 | 使用 tmux 后台运行 |

### 5.2 替代方案（若不补全数据）

如果补全成本过高，可考虑训练策略调整：

1. **缩短训练时间范围**: 仅使用 2025年1-6月 + 8-10月（避开缺失月份）
2. **降低缺失月份采样权重**: 在 `dataset.py` 中降低包含 3月/7月/11-12月 的时间窗口采样概率
3. **增加 source dropout 概率**: 当前 `student_source_drop_rate=0.3`，可提高到 0.5 以适应更多单源/双源样本

---

## 六、建议

**强烈建议执行补全**，原因：
1. S2 的 11-12 月缺失是**人为日期限制**，数据本身存在，补全成本低
2. 补全后 2025 年全年数据覆盖率将从 **66%** 提升到 **90%+**
3. 冬季（11-12月）是哈尔滨地表变化的关键期（结冰/积雪），缺失会严重影响变化检测能力

**最小可行补全**: 至少补全 S2 的 11-12 月（P0任务），这是性价比最高的改进。
